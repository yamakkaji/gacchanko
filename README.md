# がっちゃんこ gacchanko

がっちゃんこ（gacchanko）は、AIコーディングエージェントの力を借り、既存のプログラムやライブラリを組み合わせて、新しいソフトウェアを作るためのGUIアプリケーションです。

使いたいプログラムのフォルダや、これから作りたいプログラムの構想をノードとしてキャンバスへ置き、線で繋ぎ、「何をどう連携させたいか」を書きます。その設計を、普段使っているCodexやClaude CodeなどのAIコーディングエージェントへ渡すと、エージェントがコードを調べ、接続に必要な実装を作ります。

がっちゃんこ自体にLLMのAPIキーは必要ありません。設計と生成された実装は、ローカルのプロジェクトとして管理できます。

Tauri 2を使った実験的なデスクトップアプリケーションです。macOS版をローカルでビルド検証し、Windows版のビルドはGitHub Actionsに対応しています。Windowsでの実機動作は未検証です。接続コードの生成には、対象のローカルファイルを読み書きできるAIコーディングエージェントを別途用意してください。

## 序文

我々が何かを作るときにやっていることは、大まかに見れば、要素を作ることと、要素同士を繋げることである。そして、要素とその繋がりをひとまとめにして新たな要素とし、それをさらに他の要素と繋げることで、より複雑なものを作り出している。これは、プログラミングでいえば、オブジェクト指向であろうと関数型であろうと共通する見方である。生物の進化にも、要素とその関係の変化を見ることができる。多種多様なタンパク質の機能だけでなく、それらの発現や相互作用を調節する仕組みも進化してきたことで、私たちの身体は成り立っている。

このように何かを作ることを捉えたとき、創造性が問われるのは、「どのような要素を作り出すか」と「何と何を、どのように繋げるか」である。さらに、要素の内部にも既存の要素の組み合わせがあると見るならば、新たな要素を作ることも、その内部の組み合わせを考えることとして捉えられる。実際に、プログラミングで新しいものを作るとき、既存のライブラリや仕組みを組み合わせることで、個々の要素だけでは実現できなかった機能や振る舞いが生まれる。その成果物が次の創造に使われる要素となることで、組み合わせの可能性も広がっていく。ここでは、技術進化などを論じる「組み合わせ進化」の考え方に沿って、創造性をこのような過程から捉える。

ただし、何と何を繋げるかを思いつくことと、それを実際に動くものとして実装することの間には、多くの作業がある。例えば、新しく開発した画像処理アルゴリズムに、カメラ、キーボード、マウス、ディスプレイを組み合わせ、カメラが捉えた映像を編集するGUIソフトウェアを作りたいとする。このとき、カメラから映像を取得し、画像処理アルゴリズムが受け取れる形式に変換し、操作に応じて処理を変更し、その結果を画面に表示する必要がある。さらに、処理速度の違いや実行のタイミング、エラーへの対処なども考えなければならない。これらの実装にも、また様々なライブラリを組み合わせる作業が必要になる。頭の中で「カメラ→画像処理アルゴリズム→ディスプレイ」と考えられても、その接続を実装する負担は小さくない。

ここで、接続には二つの側面がある。一つは、何を渡し、いつ処理し、どのような振る舞いを生み出すかという設計である。同じ要素を使っていても、順序やタイミング、フィードバックの仕方が変われば、できるものは変わる。もう一つは、その設計を実現するために、データ形式の変換や呼び出し処理、同期やバッファリングなどをコードとして実装することである。両者は完全に分離できるものではなく、実装中の発見によって設計が変わることもある。それでも、接続の実装にかかる負担を減らすことができれば、何と何をどのように組み合わせるかを考え、実際に試すことに、より多くの時間と労力を割けるはずである。

接続の負担を減らす代表的な方法として、共通のプラットフォームや規格を用意することが挙げられる。要素が同じインターフェースに従っていれば、それらを繋げる作業は容易になる。一方で、独立に開発されたプログラムが、最初から同じ規格に従っているとは限らない。既存の要素を規格に合わせて改修したり、特定のプラットフォームへ移植したりすること自体が負担となり、試せる組み合わせを制限することもある。

そこで、ここでは、LLMを基盤とするAIコーディングエージェントを用いて、接続に必要な実装をその都度作るアプローチを考える。AIコーディングエージェントは、参照先のコードと接続の意図を読み取り、要素同士の違いを埋めるラッパーや中継処理を実装する役割を担う。必要なのは、個々の要素を参照できることと、それらをどのように組み合わせたいかが記述されていることである。その情報をもとに、接続に必要なコードの調査、実装、動作確認を進める。もちろん、仕様の不足や実行環境によっては追加の確認や修正が必要になるが、接続のための実装を一つずつ人が書く負担を減らせる可能性がある。

「がっちゃんこ gacchanko」は、この過程を支援するための実験的なソフトウェアである。AIコーディングエージェントには自然言語で指示できるが、多くの要素とその接続関係を文章だけで説明し、変更を追い続けるのは大変である。そこで、Max/MSPやUnreal Engine BlueprintのようなグラフUIを参考に、要素をノード、接続をエッジとして配置し、それぞれに役割や意図、条件を記述できるようにする。

例えば、カメラとディスプレイをノードとして置き、その間をエッジで繋ぐ。そして、カメラから取得した映像をどの形式で渡し、どの程度の頻度で画面を更新したいかなどを記述する。このグラフと記述はJSONファイルや指示書として保存され、普段使っているAIコーディングエージェントへ渡される。エージェントはそれをもとに参照先のコードを確認し、映像の取得から表示までを繋ぐ実装を作り、動作確認の結果を記録する。

このソフトウェアでは、エッジにもノードと同様に仕様と実装を持たせる。エッジはデータや処理の流れを示すとともに、その接続を成立させるラッパーやミドルウェアの実装先にもなる。これにより、何をどう繋ぎたいのかという意図と、そのために何が実装されたのかを対応づけて扱えるようにする。

がっちゃんこは、あくまでこの考え方を試すための実験的な実装である。何と何を、どのように繋げるかという構想を、接続の実装負担によって諦めなくてよくすること。そして、試した組み合わせから、次の組み合わせに使える新たな要素が生まれていくこと。このソフトウェアが、そのような創造の過程を少しでも支えられればと願う。

## インストールと起動

配布用インストーラーは [GitHub Releases](https://github.com/yamakkaji/gacchanko/releases) で公開します。対応するリリースがまだない場合は、以下の手順でソースからビルドしてください。GitHub Actionsの「Desktop builds」でもビルド成果物を取得できます。

**配布済みのTauri版を使うだけなら、Rust・Node.js・Git・Xcode Command Line Toolsは不要です。** Git履歴の処理はアプリに組み込んだlibgit2が行います。接続するプログラムや生成コードに必要な実行環境は別途用意してください。

ソースからのビルドにはNode.js、npm、Rust stableと、[TauriのOS別ビルド環境](https://v2.tauri.app/start/prerequisites/)が必要です。

- macOS 13以降：Xcode Command Line Tools。Tauriでも開発・ビルド時には必要です。
- Windows：Visual Studio C++ Build ToolsとWebView2。配布インストーラーはWebView2がない場合にダウンロードできます。
- Linux：今回の配布・実機検証の対象外です。

```sh
git clone https://github.com/yamakkaji/gacchanko.git
cd gacchanko
npm ci
npm run dev
```

配布用ビルド：

```sh
npm run build
```

生成先は `src-tauri/target/release/bundle/` です。macOSでは `macos/gacchanko.app` とDMG、Windowsではインストーラーが生成されます。OSごとのビルド環境で実行してください。

更新時はアプリを終了して `git pull --ff-only`、`npm ci`、`npm run build` を実行します。

従来のSwift版は `Sources/` と `build.sh` に残しています。Macで `./build.sh` を実行すると `dist/gacchanko.app` が生成されます。既存の `.gacchanko` プロジェクト形式はTauri版と共通ですが、外観・言語などアプリ側の設定は保存領域が異なるため再設定してください。同じプロジェクトを両方のアプリで同時に編集することは避けてください。

作成する `.gacchanko` プロジェクトは、このリポジトリの外へ保存すると、アプリのソースと分けて管理できます。

<a id="first-steps"></a>

## 最初の使い方

1. **要素を置く。** Finderから使いたいプログラムのフォルダをキャンバスへドロップします。「＋ コンポーネントを追加」からURLや、まだ実装のない構想も追加できます。
2. **線で繋ぐ。** ノードの右側の出力ポートから、左側の入力ポートへドラッグします。出力、入力の順にクリックしても接続できます。
3. **意図を書く。** ノードや線を選び、右側のInspector（詳細パネル）で名前やDescriptionを入力します。何を渡すか、どう処理したいか、必要な条件などを書いてください。
4. **保存する。** 「保存」で `.gacchanko` プロジェクトフォルダを作ります。保存後の編集は自動保存されます。
5. **エージェントへ渡す。** 「エージェントに渡す」を押し、コピーされた依頼文をCodexやClaude Codeなどへ貼り付けます。ローカルファイルを読み書きできる環境で、対象プロジェクトへのアクセスを許可してください。
6. **結果を確認する。** エージェントが接続コードと検証レポートを保存すると、アプリに実装状態や確認結果が反映されます。設計を変更したら、再び実装・検証を依頼できます。

選択したノードや接続だけを依頼する場合は、Inspectorの「このコンポーネントをエージェントに渡す」を使います。接続のないノードにも使えます。

初回画面の「サンプルを開く」では、画像・音声・テキストを入力するLLMエージェントの設計例を試せます。[サンプルのプロジェクト](examples/Multimodal-agent.gacchanko)もアプリの「開く」から利用できます。これは構成を示す例であり、参照先のコードやモデルを設定して、エージェントに実装を依頼する必要があります。

<a id="language-and-tutorial"></a>

## 言語とチュートリアル

「設定 → Language / 言語」で日本語と英語を切り替えられます。画面・アプリのメニュー・エージェントへの依頼文に反映され、次回起動時も選択を保持します。ノード名や説明など、プロジェクトに記入した内容は翻訳されません。OS標準のファイル選択画面の一部はOSの言語設定に従います。

使い方はアプリ内の「チュートリアル」でも確認できます。ノードとエッジ、追加と接続、Inspector、保存とエージェントへの受け渡し、結果の確認を6ステップで案内します。チュートリアルは上部メニュー、左下のボタン、空のキャンバス、ヘルプから開けます。

<a id="canvas-controls"></a>

## キャンバスの操作

- **Shift＋クリック**：ノードの追加選択・選択解除。
- **空白をドラッグ**：四角に全体が入ったノードを一括選択。Shift を押すと現在の選択に追加。
- **選択したノードをドラッグ**：まとめて移動。Delete で一括削除、⌘Z で元に戻す。
- **Space＋ドラッグ / 中ボタンドラッグ**：画面を移動。トラックパッドのスクロールでも移動。
- **線を選んで接点をドラッグ**：入力側・出力側を付け替え。1本だけつながった入力ポートは直接ドラッグでも付け替え。
- **ポートの近くで離す**：互換性のあるポートに吸着して接続。不適切なポートやキャンバス外で離した付け替えは元に戻ります。
- **新しい線を空白で離す**：ノード追加画面を開き、その位置に追加したノードへ自動接続。ノードとエッジの追加は1回のUndoで取り消せます。
- **付け替え中の線を空白で離す**：その端を未接続として保持。エッジのID・Description・設計指示・実装ファイル・見た目は保持し、未接続の丸い端点から再接続できます。両端が未接続でも保存でき、再起動後も残ります。
- **Esc**：範囲選択や接続操作をキャンセル。

エッジは出力から入力へ線に沿って色が変わります。要求・応答の接続はラベルの ↔ と出力側の戻り矢印、実装状態はラベル横の色付きの点で表示します。

左下の「設定」で、エッジの表示をプレビューしながら調整できます。

- グラデーション / 模様 / 両方 / 状態色の切り替え。
- out 側・in 側・模様の色。
- 山形・先細りストライプ、模様の大きさと間隔、線の太さ。
- 矢印の表示・非表示、初期設定へのリセット。

表示設定はこのアプリのローカル設定として保持し、再起動後も復元します。プロジェクトのグラフやエージェント用仕様には含めません。線の太さと模様の大きさ・間隔は縮小表示でも保ちます。

<a id="node-appearance"></a>

### ノードとエッジの外観

ノードを選択し、インスペクタ最下部の「見た目を変更…」を押すと、任意のアクセント色（カラーピッカー／HEX）、角の丸み（0–28px）、対角の非対称、塗り・枠線・影、タイトルバーの縞模様を変更できます。Shiftや矩形選択で複数ノードにまとめて適用できます。標準に戻す、Undo/Redoにも対応しています。

設定は各ノードの `appearance` に保存され、原型から作成するvariantにも引き継がれます。immutableでも外観は変更でき、実装レポートは要更新になりません。外観変更はGit履歴に記録されます。

ノードの色は選んだHEX値のままベタ塗りされます。文字は背景とのコントラストに応じて白・黒を自動選択します。「枠線」では本体を白にし、タイトルバーに選択色を使用します。

エッジもInspector最下部の「見た目を変更…」から個別に設定できます。個別設定はプロジェクトに保存され、設定しない場合はアプリ全体の表示設定が使われます。

<a id="component-inspector"></a>

## コンポーネントの設定

ノードとエッジをともに「コンポーネント」と呼びます。選択すると、Inspectorに共通の項目が表示されます。以下は英語表示での項目名です。

| 項目 | 内容 |
|---|---|
| Component Name | コンポーネント名 |
| Mutability | `mutable`（編集可能）または `immutable`（保護） |
| Implementation | `implemented`（実装済み）または `not implemented`（未実装）。ユーザーによる申告で、自動検証の結果ではありません |
| Component Type | ノードの種類、またはデータの受け渡し・要求と応答・イベントといった接続の形式 |
| Access | ディレクトリパス、URL、IPアドレスなどの参照先。入力だけでは接続・実行しません |
| Description | 要素の役割や接続の意図、満たしてほしい条件 |

「ノードの詳細…」では設計指示・起動方法・入出力ポートを、「接続の詳細…」では設計指示や同期・非同期の条件を編集できます。接続中のポートは、その接続を外してから削除・改名してください。

ノードとエッジのどちらでも、Inspectorからエージェントへ依頼し、実装レポートや確認記録を閲覧できます。

<a id="design-checks"></a>

### 接続の入力と設計チェック

線をつなぐと他のコンポーネントと共通のInspectorを表示し、Descriptionへ接続の意図を記入できます。左の「設計チェック」で不足一覧を表示し、ノードは赤い外周、接続は赤いラベルで強調します。一覧をクリックすると対象の入力欄へ移動します。エージェントへの受け渡し前も同じ検査を行い、未確定のまま相談する場合は明示的に続行できます。これは記述の検査で、コードの動作検証ではありません。

ノードの実装状態は「implemented / not implemented」から選び、キャンバスにも表示します。パスやREADMEが存在するだけでは実装済みと判定しません。

<a id="execution-layers"></a>

## 接続レイヤーと非同期設計

キャンバス上部でデータ・実行制御・イベントを切り替え表示できます。接続のInspectorから「接続の詳細…」を開き、同期／非同期、完了待ちの接続、all／any、最大並列数、期限、キュー上限、満杯時と失敗時の処理を設定します。完了待ちの循環は保存時に拒否します。反復はイベントと開始・終了条件で指定してください。

設定は `graph.json` と各 `SPEC.md` に出力します。意味とJSON例は [実行仕様](docs/workflow-contract.md) を参照してください。アプリ内で実行するスケジューラーではなく、依頼先エージェントが実装するための仕様です。

<a id="design-and-history"></a>

## 設計の属性・原型・変更履歴

`mutable` は編集可能、`immutable` は設計を保護する属性です。保護の解除には確認が必要です。ノードやエッジの外観は、保護された状態でも変更できます。

複数ノードと内部の接続を**原型（template）**として登録し、同じ構成を引き継ぐ**派生版（variant）**を作れます。原型の版・各要素との対応・設計指示はプロジェクトに保存され、エージェントにも渡されます。[原型と派生版のサンプル](examples/Template-variants.gacchanko)で構成を確認できます。

設計・実装・レポートはプロジェクト内のGit履歴へ自動記録されます。「変更履歴」から追加・変更・削除やコードの差分を確認できます。

外部のエージェントがグラフを変更すると、アプリはその変更を提案として通知します。「比較・採用」で変更前後を確認し、取り込む内容を選べます。保護違反や接続先が欠ける組み合わせは採用できません。未保存の編集がある場合は、提案を退避して先に保存するか、編集をJSONで退避してください。

`immutable` はアプリの編集・保存処理とプロジェクト内の対応する実装を保護するための仕組みです。同じファイル権限を持つ外部プロセスの書き込みや、参照先リポジトリの変更を禁止するものではありません。

詳細は[設計の属性・原型・変更履歴](docs/design-versioning.md)を参照してください。

<a id="agent-handoff"></a>

## 接続実装のサンプル

形式の異なる2つのローカルプログラムをラッパーで繋ぐ[サンプルと実行手順](examples/agent-handoff/README.md)を用意しています。依頼用プロジェクトの作成から、コードの実装、実行テスト、レポートの反映までを試せます。

このサンプルにはPython 3.10以降が必要です。動作確認用の実装例も含まれるため、その実装を試すだけならLLMや外部APIは不要です。

<a id="scope"></a>

## 現在の対応範囲と制約

がっちゃんこは、グラフによる設計、エージェントへの受け渡し、実装結果の確認を支援する実験的なアプリケーションです。

- **コードの生成と実行はエージェント側で行います。** アプリ内にLLMや実行スケジューラーはありません。同期・非同期の設定は、生成コードに求める仕様として渡されます。
- **エージェントへの依頼は手動です。** コピーされた依頼文を、利用しているセッションへ貼り付けます。チャットへの自動送信は行いません。
- **参照先の自動解析には対応していません。** フォルダ追加時にはREADMEの先頭部分を説明欄へ取り込みます。APIやポートの調査はエージェント側で行います。URLを指定しても自動cloneは行いません。
- **実装状態は申告・レポートに基づきます。** アプリ自身が生成コードの正しさを検証するものではありません。参照先のコードを更新したときは、エージェントへ再検証を依頼してください。
- **別のマシンへ移す際にはパスを確認してください。** 参照先は絶対パスで保存されるため、移動先に合わせた設定が必要です。

<a id="project-files"></a>

## ファイルの構成

| ファイル / フォルダ | 役割 |
|---|---|
| `graph.json` | グラフの正本。ノード、参照先、ポート、エッジの意図を格納 |
| `AGENT_BRIEF.md` | 全体の目的、参照先、作業方法をまとめた生成文書 |
| `connections/<edge-id>/SPEC.md` | 接続ごとの仕様と fingerprint |
| `implementations/<edge-id>/` | エージェントが実装を書く場所 |
| `implementations/shared/` | 接続間で共有するコードの保存先 |
| `reports/<edge-id>.json` | エージェントによる実装・検証の報告 |
| `graph.mmd` | 設計を読むための Mermaid 出力 |
| `components/nodes/<node-id>/SPEC.md` | ノードごとの仕様と fingerprint |
| `components/nodes/<node-id>/implementation/` | ノード単体の生成コード |
| `components/nodes/<node-id>/report.json` | ノード単体の実装・検証レポート |

エージェントは `AGENT_BRIEF.md` と `graph.json` を読み、元のプログラムのコードと適用される指示を確認します。元リポジトリを変更しなくても接続コードを管理できます。生成された仕様文書を直接編集しても次の保存で更新されるため、設計の変更は GUI または `graph.json` へ行ってください。

<a id="report-format"></a>

## レポートの形式

`reports/<edge-id>.json` に、次の形式で保存します。

```json
{
  "fingerprint": "connections/<edge-id>/SPEC.md に記載された値",
  "status": "implemented",
  "summary": "実装したことと残っていること",
  "files": ["implementations/<edge-id>/adapter.py"],
  "checks": ["実際に実行した確認コマンドと結果"]
}
```

- `implemented` は実装済み、`verified` は関連する確認を実際に実行済み、`blocked` は未解決事項あり、を表します。
- エッジの仕様、接続するノードの説明・参照先・ポート、または全体の目的を変えると fingerprint が変わり、古いレポートは「要更新」として表示されます。位置・ノードの外観変更では変わりません。
- 状態はエージェントが報告した結果です。GUI 自身が検証を行うわけではありません。構文検査だけで実際の統合実行が成功したと報告しないよう、指示書にも明記しています。
- **参照先リポジトリのソース変更は自動監視しません。** コードを更新した場合は、再検証を依頼してください。
- エッジを削除しても、その実装と以前のレポートは残します。有効な接続は常に `graph.json` を基準に判断します。

ノード単体のレポートも同じ形式で、ノード自身の `SPEC.md` にあるfingerprintを使用します。保存先は上のファイル構成を参照してください。

<a id="development"></a>

## 開発と検証

```sh
npm ci
npm run test:store
npm run test:ui
npm run dev
```

Rustの保存処理のテストでは、保存・仕様書・レポート・履歴、外部提案の比較と部分採用、再起動後の提案保持、immutable保護、明示的な保護解除、シンボリックリンクへの書き込み拒否を確認します。UIテストでは既存の編集操作に加え、Tauriアダプターの通信とイベントも確認します。

実際のWebViewとRustを通すテストはGUIを起動できる環境で実行します。以下はmacOSの例です。テスト専用コマンドはデバッグビルドにのみ含まれます。

```sh
npm run test:native
```

Swift版との比較結果・既知の差分は[互換性とテスト範囲](docs/tauri-parity.md)に記載しています。ネイティブのファイル選択、ドラッグ＆ドロップ、終了確認、Windowsの表示倍率とパスの扱いは実機で確認してください。テストで生成した `verified` レポートはテスト用fixtureであり、エージェント実装の検証結果ではありません。

Swift版とのfingerprint・履歴互換テストはmacOSで実行できます。

```sh
mkdir -p .build/module-cache
xcrun swiftc -module-cache-path .build/module-cache Sources/Localization.swift Sources/Project.swift tests/store-driver/main.swift -o .build/store-driver
cargo build --manifest-path src-tauri/Cargo.toml --no-default-features --example store-driver
node tests/tauri-compat.cjs
```

GitHub ActionsはMac（Apple Silicon / Intel）とWindows x64をビルドします。`v*` タグをpushすると、成功したインストーラーを下書きのGitHub Releaseへ添付します。公開前に実機確認とリリース内容の確認を行ってください。現時点ではApple Developer ID署名・公証、Windowsコード署名は設定していません。配布時の注意は[リリース案内](docs/tauri-release.md)を参照してください。

## 実装構成

画面はHTML / CSS / JavaScript、デスクトップのホストと保存処理はTauri 2 / Rustです。WebサーバーやNode.jsを常駐させず、OSのWebViewで画面を表示します。

- `web/`：共通のグラフ編集画面。`tauri.js` がTauriを検出し、`bridge.js` の共通インターフェースへ接続します。
- `src-tauri/src/main.rs`：ファイル選択、クリップボード、ドロップ、メニュー、終了確認。
- `src-tauri/src/store.rs`、`graph.rs`、`history.rs`：保存、仕様書、検証、fingerprint、libgit2によるプロジェクト内の履歴。
- `Sources/`：比較・互換確認用に保持している従来のSwift版。

通信コマンドと各部分の役割は[設計文書](docs/architecture.md)を参照してください。
